📖 一、Skill 是什么

把 Claude Code 从通用助手变成领域专家

Skill（技能）是 Anthropic 于 2025 年 10 月 16 日 为 Claude Code 正式发布的功能，随后于 12 月 18 日，Agent Skills 规范作为开放标准发布在 agentskills.io，目前已有 30+ 平台采纳支持。

📌 核心定义Skill 的本质非常简单：一个包含 SKILL.md 文件的目录，就是一个 Skill。

SKILL.md 文件由两部分组成：

组成部分内容作用
YAML Frontmatter被 --- 包裹的元数据定义 Skill 的名称、描述、触发条件、可用工具等
Markdown 正文指令和模板内容告诉 Claude 在 Skill 激活时应该做什么、怎么做

用大白话说：Skill 就是你提前写好的"工作说明书"，告诉 Claude Code 在特定场景下如何更好地帮你完成任务。比如：

  • 你可以写一个代码审查 Skill，让 Claude 每次审查代码时都按照统一的标准和格式
  • 你可以写一个 Git 提交 Skill，让 Claude 帮你生成规范化的 commit message
  • 你可以写一个技术文档 Skill，让 Claude 帮你按照团队规范编写 API 文档

Skill 是如何工作的？

当你与 Claude Code 对话时，系统会检查当前可用的所有 Skill（根据目录层级确定），并读取每个 Skill 的 description 字段。如果你输入的内容与某个 Skill 的描述高度匹配，Claude Code 就会自动激活该 Skill，将 SKILL.md 中的指令注入到当前的对话上下文中，从而按照你预定义的规范来响应。

这个过程对用户是完全透明的——你只需要正常使用 Claude Code，合适的 Skill 会在恰当的时机自动生效。

✅ 核心原则写好一次，每次对话都能用；别人写好的，装上就能用。

Skill 的核心特点

Skill 功能之所以强大，源于三个核心设计特点：

🔄 可复用（Write Once, Use Everywhere）

写好一个 Skill 之后，每次与 Claude Code 对话时都可以使用它，不需要每次都重复输入冗长的指令。比如你有一个写单元测试的 Skill，一旦配置好，任何时候你说"帮我写测试"，Claude 都会自动按照你定义的模板和规范来生成。

🔗 可分享（Share & Reuse）

Skill 本质上是文本文件（SKILL.md），可以很方便地：通过 Git 仓库分享给团队成员、发布到 GitHub 上供社区使用、通过插件市场一键安装。你不需要从零开始——社区已经有大量现成可用的 Skill。

⚡ 自动触发（Auto-match & Manual Trigger）

Skill 有两种激活方式：自动触发（Claude Code 根据你的输入内容自动判断哪个 Skill 最合适）和手动触发（通过斜杠命令如 /commit-msg 主动激活）。判断依据是 SKILL.md 中 description 字段的内容——描述越准确，自动匹配率越高。

💡 小贴士description 字段是自动触发的灵魂，建议认真填写。前 1536 个字符会被系统读取，超出部分会被截断，所以要在这有限的篇幅内描述清楚 Skill 的适用场景。

Skill 与 Plugin、MCP 的区别

初学者最容易混淆的三个概念是 Skill、Plugin 和 MCP。下面是清晰的对比：

🧩 Skill vs Plugin

维度Skill（技能）Plugin（插件）
本质能力模块容器/集合
结构一个目录，核心是 SKILL.md一个目录，核心是 plugin.json
内容SKILL.md + 可选的 scripts/、references/、assets/ 等多个 Skill + hooks + agents + MCP servers
安装单位单个 Skill整个 Plugin（含多个组件）
使用方式安装后自动或手动触发安装后内部所有 Skill 同时生效

简单类比：Skill 像是一把螺丝刀（单一工具），Plugin 像是一个工具箱（包含螺丝刀、锤子、钳子等一整套工具）。安装一个 Plugin，等于一次性安装了其中包含的多个 Skill 和其他组件。

🌐 Skill vs MCP

维度SkillMCP
定位流程层/知识层外部连接层
作用定义"怎么做"（工作流程、规范、模板）定义"连接什么"（外部数据源、工具、API）
示例代码审查规范、提交信息模板、文档格式连接数据库、读取文件系统、调用外部 API

两者是互补协同的关系：Skill 告诉 Claude "按什么流程和规范来做事"，MCP 告诉 Claude "可以去哪里获取数据和使用什么外部工具"。在实际项目中，两者经常搭配使用。

⚠️ 注意事项不要把 Skill 和 Plugin 混为一谈。Skill 是 Plugin 的组成部分，但 Skill 可以独立存在和使用，而 Plugin 是一个更大的容器概念。

📦 二、怎样安装 Skill

Skill 文件应该放在哪里？怎么装别人的？怎么创建自己的？

2.1 Skill 文件应该放在哪里

Claude Code 支持四层目录结构来存放 Skill，每一层对应不同的作用范围和优先级：

级别存放路径作用范围适用场景
企业级托管设置（Managed Settings）整个组织公司统一规范，全员生效
用户级~/.claude/skills/<skill-name>/SKILL.md所有项目个人常用 Skill，全局可用
项目级.claude/skills/<skill-name>/SKILL.md当前项目项目特定的工作流和规范
插件级<plugin>/skills/<skill-name>/SKILL.md随插件生效安装插件时自动部署
📌 优先级规则当同名 Skill 存在于多个层级时，Claude Code 按照以下优先级加载（优先级高的覆盖优先级低的）：
企业级（Enterprise） > 用户级（Personal） > 项目级（Project）

对于大型单体仓库（Monorepo），Claude Code 还支持嵌套的 .claude/skills/ 目录。你可以在子项目目录下也创建 .claude/skills/，这些 Skill 只对所在子项目生效，实现了更精细的权限控制。

# 用户级 Skill 目录结构
~/.claude/
└── skills/
    ├── commit-msg/
    │   └── SKILL.md
    ├── code-review/
    │   └── SKILL.md
    └── doc-writing/
        └── SKILL.md

# 项目级 Skill 目录结构
my-project/
├── .claude/
│   └── skills/
│       ├── deploy-guide/
│       │   └── SKILL.md
│       └── test-template/
│           └── SKILL.md
├── src/
└── package.json
💡 小贴士建议将通用型 Skill（如写 commit message、代码审查）放在 ~/.claude/skills/（用户级），而将项目专属 Skill（如项目部署流程、团队编码规范）放在项目级的 .claude/skills/ 目录下，并通过 Git 版本控制与团队共享。

2.2 安装别人的 Skill

当你从 GitHub、同事或社区获取到一个现成的 Skill 时，有三种安装方式可选。

方式一：手动复制

最基础的方式，适用于所有 Skill。步骤如下：

  1. 获取 Skill 文件夹 — 通过 git clone 或下载 ZIP 包
  2. 复制到对应目录 — 根据需求选择用户级或项目级路径
# 第1步：从 GitHub 克隆 Skill 仓库
git clone https://github.com/author/skill-name.git

# 第2步：复制到用户级目录（所有项目可用）
cp -r skill-name ~/.claude/skills/

# 或者复制到项目级目录（仅当前项目可用）
cp -r skill-name .claude/skills/

安装完成后，Skill 立即生效，Claude Code 会根据匹配条件自动调用。

⚠️ 注意事项确保复制的是整个 Skill 目录（包含 SKILL.md 的文件夹），而不是只复制 SKILL.md 单个文件。正确的目录结构应该是 ~/.claude/skills/my-skill/SKILL.md，而不是 ~/.claude/skills/SKILL.md。

方式二：用第三方工具一键安装

Vercel Labs 开发了一个便捷的 CLI 工具，可以通过命令行一键安装 Skill。

GitHub 仓库：https://github.com/vercel-labs/skills

# 基本语法
npx skills add <github-repo> --skill <skill-name>

# 示例：安装指定 Skill
npx skills add author/repo-name --skill my-skill

# 全局安装（放入 ~/.claude/skills/）
npx skills add <github-repo> --skill <skill-name> -g

# 项目级安装（放入 .claude/skills/）
npx skills add <github-repo> --skill <skill-name>

安装过程是交互式的，工具会引导你依次选择：

  1. 选择 Agent（如 Claude Code）
  2. 选择 Scope（全局或项目级）
  3. 选择安装方式（symlink 软链接 / copy 复制）
💡 小贴士你也可以使用 bunx 或 pnpm dlx 替代 npx，效果相同。
⚠️ 注意事项该工具可能存在一个已知问题——有时不会自动创建 symlink（参考 GitHub Issue #851）。如果遇到 Skill 安装后无法触发的情况，可以尝试手动创建软链接：
ln -s /path/to/source/skill ~/.claude/skills/<skill-name>

方式三：安装插件

通过 Claude Code 的插件市场安装包含 Skill 的插件，适合安装官方或社区维护的 Skill 集合。

# 第1步：添加插件市场
/plugin marketplace add anthropics/skills

# 第2步：安装指定插件（插件名@anthropic-agent-skills）
/plugin install 插件名@anthropic-agent-skills

# 示例：安装官方文档 Skill 插件
/plugin install document-skills@anthropic-agent-skills

安装完成后，插件内包含的所有 Skill 会自动生效，无需额外配置。

2.3 创建自己的 Skill

如果现成的 Skill 无法满足你的需求，你可以轻松创建自己的 Skill。创建 Skill 有三种方式：手动编写、让 Claude Code 帮你生成、或使用 /skill-creator。

SKILL.md 文件结构

SKILL.md 是 Skill 的核心文件。一个完整的 Skill 目录通常包含以下结构：

my-skill/
├── SKILL.md           # 核心文件（必需）
├── template.md        # 模板文件（可选）
├── examples/          # 示例目录（可选）
│   └── example1.md
├── scripts/           # 辅助脚本（可选）
│   └── helper.sh
├── references/        # 参考文档（可选）
│   └── guidelines.md
└── assets/            # 静态资源（可选）
    └── diagram.png

其中，只有 SKILL.md 是必需的，其他文件和目录都是可选的，根据 Skill 的复杂程度决定是否需要。

元信息（Frontmatter）详解

Frontmatter 是 SKILL.md 文件顶部被 --- 包裹的 YAML 元数据区域，是 Skill 的"配置大脑"。完整支持 15 个字段：

字段必填类型说明
name否string显示名称，省略则用目录名。小写+数字+连字符，最多 64 字符
description推荐string功能描述，Claude 据此判断何时加载 Skill。前 1536 字有效
when_to_use否string额外触发条件描述，追加到 description 后
argument-hint否string自动补全时显示的参数提示
arguments否array命名位置参数，用于 $name 替换
disable-model-invocation否booleantrue = 禁止自动加载，仅手动触发（默认 false）
user-invocable否booleanfalse = 从 / 菜单隐藏，仅 Claude 能调用（默认 true）
allowed-tools否arraySkill 激活时无需确认即可使用的工具列表
model否stringSkill 激活时使用的指定模型
effort否string思考力度：low / medium / high / xhigh / max
context否string设置为 fork 在独立 subagent 中运行
agent否stringcontext: fork 时使用的 subagent 类型
hooks否objectSkill 生命周期钩子（激活前/后执行的操作）
paths否arrayGlob 模式，仅当匹配到指定文件时自动激活
shell否string!command 使用的 shell：bash 或 powershell
📌 最核心的字段：descriptiondescription 直接决定了自动触发的准确率。建议遵循以下原则：
• 明确说明 Skill 的功能
• 列举触发场景（"当用户要求 XXX 时使用"）
• 使用关键词描述适用领域
• 控制在 1536 字符以内（超出部分会被截断）

常用字段组合示例：

# 对于只希望在特定情况下自动激活的 Skill：
---
name: api-doc
description: 为 REST API 编写接口文档。当用户要求编写 API 文档、接口说明或更新接口定义时使用。
paths: ["**/openapi.yaml", "**/swagger.json", "**/routes/**"]
---

# 对于需要额外工具权限的 Skill：
---
name: deploy-check
description: 在部署前执行检查清单。当用户提到部署、上线、release 或 deploy 时使用。
allowed-tools: ["Bash", "Read", "Glob"]
effort: high
---

正文编写指南

Frontmatter 之后是 Markdown 正文部分，这里是 Skill 的"灵魂"——告诉 Claude 激活后应该做什么。

编写原则：

  1. 指令清晰：明确告诉 Claude 任务目标、步骤和输出格式
  2. 格式规范：使用 Markdown 的标题、列表、代码块来组织内容
  3. 示例驱动：提供输入输出示例，让 Claude 理解期望的结果样式
  4. 约束明确：指定字数限制、格式要求、风格偏好等约束条件
  5. 适度长度：正文不是越长越好，关键是信息密度高、指令无歧义。通常 50-200 行的正文已经足够描述大部分工作流
  6. 使用变量：如果定义了 arguments 字段，可以在正文中用 $变量名 引用用户传入的参数

正文结构建议：

---
# Frontmatter 区域
---
# 这里是正文
## 任务目标
简要说明这个 Skill 要做什么。

## 操作步骤
1. 第一步...
2. 第二步...
3. 第三步...

## 输出格式
指定期望的输出格式和结构。

## 示例
提供1-2个完整的输入/输出示例。

实用示例：Git 提交信息 Skill

下面是一个完整的 Git 提交信息 Skill 示例，展示了所有关键元素的实际运用：

---
name: commit-msg
description: 生成规范的Git提交信息。当用户要求写commit message、git commit、提交信息或提交代码时使用。
---
请根据当前的代码变更，生成一条规范的Git提交信息。

## 格式要求
1. 第一行用类型前缀，如 `feat`、`fix`、`docs`、`style`、`refactor`、`test`、`chore` 等
2. 简要描述改了什么，不超过 50 个字符
3. 如果改动较大，在下方补充详细说明，每行不超过 72 个字符
4. 使用中文描述

## 类型说明
| 前缀 | 用途 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档更新 |
| style | 代码格式调整（不影响功能） |
| refactor | 代码重构 |
| test | 测试相关 |
| chore | 构建/工具链/杂项 |

## 示例
feat: 添加用户登录功能
- 实现JWT token认证
- 添加登录页面表单验证
- 添加登录状态持久化

将这个文件保存为 .claude/skills/commit-msg/SKILL.md（或 ~/.claude/skills/commit-msg/SKILL.md），就可以使用了。

💡 小贴士在 description 中列举多个触发关键词（如"commit message"、"git commit"、"提交信息"），可以显著提高自动匹配的命中率。

让 Claude 帮你创建 Skill

最简单的方式——直接在对话中描述你的需求，让 Claude Code 帮你生成 Skill。

对话示例：

用户：帮我创建一个写 Git 提交信息的 Skill
Claude：好的，我来为你创建一个 commit-msg Skill。
       我会将它保存到 .claude/skills/commit-msg/SKILL.md

Claude 会自动：

  1. 分析你的需求
  2. 编写合适的 Frontmatter（尤其是 description）
  3. 编写清晰的正文指令
  4. 将文件保存到正确的位置

提高生成质量的技巧：

  • 描述要具体：不要说"帮我写个文档 Skill"，而要说"帮我写一个 Skill，用于生成 REST API 接口文档，要求包含参数说明、返回值示例和错误码表格，使用 Markdown 格式"
  • 给出示例：告诉 Claude 你期望的输出样式，比如"参考我们团队的这种格式..."
  • 指定触发条件：明确告诉 Claude 在什么场景下应该激活这个 Skill

另一种方式：使用 /skill-creator

/skill-creator

/plugin install skill-creator@anthropic-agent-skills
安装完成后，使用 /skill-creator 会进入一个交互式的 Skill 创建流程，引导你逐步完成配置。
💡 小贴士即使是让 Claude 帮你创建，也建议在生成后检查一下 description 字段是否准确描述了你的使用场景。可以手动补充一些触发关键词，提高自动匹配的准确率。

⚡ 三、怎样触发和使用 Skill

自动匹配 + 手动控制，灵活调用

3.1 自动触发机制

自动触发是 Claude Code Skill 系统最强大的特性之一。Claude 会持续监控对话内容，在适当的时候自动调用相关的 Skill。

触发原理：Claude 的自动触发遵循以下流程：

  1. 语义匹配：Claude 读取所有已安装 Skill 的 description 字段，当用户输入的内容与某个 Skill 的描述匹配时，系统自动触发该 Skill。
  2. 渐进式加载（Progressive Disclosure）：为了节省 token，Claude 不会一次性加载所有 Skill 的完整内容，而是采用三级加载策略：
层级加载内容估算大小触发条件
Level 1Frontmatter（元数据）~100 tokens/Skill每次对话自动加载
Level 2SKILL.md 正文取决于 Skill 复杂度description 匹配时加载
Level 3链接的附加文件取决于文件大小实际需要时按需加载
💡 小贴士这种渐进式设计可以降低 60%-70% 的 token 消耗。如果你的项目安装了 20 个 Skill，按全量加载可能需要数千 tokens，而渐进式加载通常只需要几百 tokens。

如何提升自动触发准确率

自动触发的核心在于 description 字段的质量。以下是经过验证的优化建议：

  • 基础版：清晰的 description —— 触发率约 20%
  • 优化版：详细描述 + 触发场景说明 —— 触发率可提升到 50%+
  • 进阶版：添加 examples 字段提供示例 —— 触发率进一步提升到 72%-90%
# 触发率较低的描述
description: "帮助写代码"

# 触发率较高的描述
description: "在需要编写符合团队规范的 Git 提交信息时自动触发，支持 Angular 提交规范，能自动生成包含类型、作用域和描述的完整提交信息"

# 触发率最高的描述（含示例）
description: "在需要编写符合团队规范的 Git 提交信息时自动触发"
when_to_use: |
  - 用户说"帮我写提交信息"或"生成 commit message"
  - 执行 git commit 前需要格式化提交信息
  - 需要遵循 Conventional Commits 规范时
⚠️ 注意事项description + when_to_use 的合计文本在 Skill 列表中会被截断至 1536 个字符。因此要把最关键的信息放在前面，避免重要内容被截断。

3.3 控制触发行为

通过 Frontmatter 中的两个关键字段——disable-model-invocation 和 user-invocable——你可以精细控制 Skill 的触发行为。

Frontmatter 配置用户可手动触发Claude 可自动触发description 是否加载
默认（无设置）是是是
disable-model-invocation: true是否否
user-invocable: false否是是
两者都设置否否否

使用场景建议：

场景一：防止自动触发（推荐用于有副作用的操作）

---
name: deploy-to-production
description: 部署应用到生产环境
disable-model-invocation: true
---

适合场景：部署代码、提交到主分支、发送邮件、执行数据库迁移等具有实际副作用的操作。这样只有在用户明确手动调用时才会执行。

场景二：仅自动触发（推荐用于背景知识型 Skill）

---
name: legacy-system-docs
description: 公司内部遗留系统的架构说明和 API 规范
user-invocable: false
---

适合场景：遗留系统文档、API 规范参考、团队编码规范等。这类 Skill 不需要手动调用，Claude 会在相关对话中自动引用它们。

场景三：完全禁用

---
name: deprecated-skill
description: 已废弃的 Skill
disable-model-invocation: true
user-invocable: false
---

适合场景：临时禁用某个 Skill（比如发现 bug 或已被替代），无需删除文件即可快速停用。

⚠️ 注意事项disable-model-invocation: true 不仅阻止自动触发，还会让 description 不被加载到上下文中。这意味着该 Skill 完全不会参与自动匹配过程，从而进一步节省 token。

C. 常见问题解答（FAQ）

Q1: Skill 和 MCP（Model Context Protocol）有什么区别？

Skill 是流程/知识层，定义的是 Claude 如何思考和行动的指南——比如代码审查的步骤、提交信息的格式规范。Skill 是文本指令，告诉 Claude "在什么情况下该做什么"。

MCP 是外部连接层，定义的是 Claude 与外部工具和服务交互的协议——比如连接数据库、调用 API、操作文件系统。

两者是互补关系：Skill 决定 "做什么"，MCP 决定 "怎么连接到外部资源"。一个 Skill 可以通过 MCP 工具来完成实际的操作。

Q2: 为什么我的 Skill 没有自动触发？

最常见的原因是 description 字段不够清晰。Claude 依赖 description 来判断何时触发 Skill。

排查步骤：

  1. 检查 description 是否准确描述了触发场景
  2. 添加 when_to_use 字段补充说明
  3. 添加 examples 字段提供具体的触发对话示例
  4. 确保 disable-model-invocation 没有被设置为 true
  5. 使用 /skills 确认 Skill 已正确安装

Q3: Skill 的优先级怎么确定？

当多个同名或功能相似的 Skill 同时存在时，按以下优先级生效：

企业级 (Enterprise) > 用户级 (User) > 项目级 (Project) > 插件级 (Plugin)

项目级的 Skill 优先级高于全局 Skill，这意味着你可以为不同项目定制专属的 Skill。

Q4: 一个项目中可以同时使用多个 Skill 吗？

可以。Claude 能够同时自动调用多个 Skill。在一次对话中，Claude 可能会根据上下文自动激活 2-3 个相关的 Skill 协同工作。

例如，当你说 "帮我审查这段代码并生成提交信息" 时，Claude 可能同时触发 code-review 和 commit-msg 两个 Skill。

Q5: 创建 Skill 需要编程能力吗？

不需要。创建 Skill 只需要会用 Markdown 编写文档。基本的 Skill 只需要一个 SKILL.md 文件，包含 Frontmatter 元数据和自然语言的指令内容。

当然，如果你想创建更复杂的 Skill（比如调用特定工具、处理复杂逻辑），了解一些基本的 YAML 配置和工具调用语法会有帮助。

Q6: Skill 安全吗？

Skill 本身是安全的——它只是文本指令，不直接执行代码。Claude 会按照 Skill 中的指导来思考和行动。

但需要注意以下几点：

  • allowed-tools 字段要谨慎配置，只授予 Skill 真正需要的工具权限
  • 安装来源不明的 Skill 时要审查内容，确保没有不当的操作指令
  • 对于有副作用的操作（如部署、删除数据），建议设置 disable-model-invocation: true

Q7: 如何分享自己创建的 Skill？

分享 Skill 有多种方式：

  1. GitHub：将 Skill 文件推送到 GitHub 仓库，其他人可以 clone 或下载使用
  2. 第三方平台：提交到 skills.sh 或 agentskill.sh 等平台
  3. 团队共享：将 Skill 放入项目的 skills/ 目录，通过 Git 与团队成员共享

Q8: 为什么 /plugin 命令打不开市场？

原因解决方法
Claude Code 版本过低更新到 1.0.33+ 版本
网络连接问题检查网络，尝试使用代理
市场源未添加执行 /plugin marketplace add anthropics/skills
插件索引加载失败重启 Claude Code 后重试

Q9: description + when_to_use 为什么被截断？

这是 Claude 的性能优化机制。所有 Skill 的 description + when_to_use 文本在加载到 Skill 列表时会被截断至 1536 个字符。超出部分不会参与触发匹配。

建议：把最重要的触发关键词和场景描述放在前面，确保在 1536 字符限制内。

Q10: 如何监控 Skill 的 token 消耗？

使用以下方法监控和优化：

/cost                # 查看当前会话的 token 消耗

优化建议：

  • 精简 description 和 when_to_use 文本
  • 使用 caveman Skill 减少整体 token 消耗
  • 删除不再使用的 Skill
  • 对背景知识型 Skill 设置 user-invocable: false
