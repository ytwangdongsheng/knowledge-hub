📥 一、Context 与 Context Window

先分清「模型的输入」和「输入的容量上限」

单纯从外部来看，大模型就像是一个函数：你给它输入，它就会给你输出。

🎬 00:25 · 大模型就像一个函数：输入 → 输出

不过大模型的输入是有大小限制的，这个限制叫做上下文窗口，对应的英文为 Context Window。

📌 Context：模型的输入

这里的 Context 指的就是模型的输入，它包含的内容比一般人想象的要多：

🎬 00:45 · Context = 模型输入：用户问题、背景信息、相关资料、可用工具列表、工具执行结果、历史对话
  • 用户问题 —— 当前这一轮用户说的话
  • 背景信息 —— 系统提示词、角色设定等
  • 相关资料 —— 检索回来的文档片段
  • 可用工具列表 —— 模型可以调用的工具定义
  • 工具执行结果 —— 工具调用返回的内容
  • 历史对话 —— 之前几轮的问答记录

模型把这些输入作为上下文，并基于这些内容来生成答案。

📏 Context Window：输入的容量上限

🎬 01:00 · Context Window = 模型的输入中最多能包含的 Token 数量

Context Window 指的是模型的输入中最多能够包含的 Token 数量。

Token 可以理解为文本被拆分成的最小单位，可能是一个字、一个词，或者是一个标点符号。 一个 Token 大概相当于 0.75 个单词，或者是 1.5 个汉字。

⚠️ 超过限制会发生什么 一旦超过这个限制，前面的内容就会被丢弃，只会保留最后的 N 个 Token。 也就是说，超长输入不是「截断报错」，而是「悄悄忘掉最早的内容」。

以 Gemini 2.5 Pro 为例，它的 Context Window 是 100 万，意思是它最多能够处理 100 万个 Token 的输入。

🎬 01:10 · Gemini 2.5 Pro：1,000,000 Context Window

100 万个 Token 其实是一个相当大的容量，接近几本书的长度 —— 像 Gemini 2.5 Pro 这样的模型，可以一次装下好几本书。这个容量已经非常惊人了。

💡 由此产生的直觉（以及它的错误） 既然 Context Window 这么大，那是不是就可以把所有资料都丢进去，让模型自己去理解呢？
—— 作者给出的答案是：不对，事实没有那么简单。

🚧 二、为什么不能全塞进去：三大现实问题

想让模型稳定、高效、准确地输出，绕不开这三件事

举个具体例子：假设你想做一个智能客服，希望它能回答用户提出的各种关于你们公司产品的问题。 大模型虽然很强，但直接问它的话，它只能回答「不知道」—— 毕竟它没有你们公司产品的信息。

你一想：没关系，我们不是有产品使用手册吗？直接丢给大模型就好了，让它根据手册来回答问题。 不管手册有几十页、几百页甚至上千页，都可以直接丢给模型，不用管哪些内容和用户问题相关、哪些不相关。

🎬 02:10 · 用户提问「你们产品的保修期多长？」，把产品使用手册直接丢给大模型

反正 Context Window 这么大，全部丢给它就行了 —— 这看起来没问题，但实际上行不通。 在实际使用过程中，我们仍然会遇到很多限制，必须考虑三个非常现实的问题：

🎬 04:00 · 三大问题：窗口有限、输入杂乱、成本上升

1️⃣ 大多数模型的 Context Window 非常有限

Gemini 2.5 Pro 的 100 万 Context Window 算是很大的了，大部分模型其实都没有这么大。 看看主流模型的实际大小：

🎬 03:12 · 主流模型的 Context Window 大小对比
模型Context Window
Gemini 2.5 Pro100 万
GPT-540 万
Deepseek V312.8 万
Claude 420 万

这些都还算是相当不错的模型了。很多时候为了节省成本，我们可能还会使用一些小模型， 它们的 Context Window 可能就只有几万 —— 连一个产品使用手册也装不下。

2️⃣ 输入太杂乱会影响模型的理解

即使你所使用的模型有着非常大的 Context Window，即使我们给模型的输入量没有超过窗口上限， 你也最好不要把所有相关资料不加筛选全部丢给模型。

因为如果不加筛选，模型的输入可能就会非常杂乱、冗余矛盾。模型这个时候可能就会混淆重点， 输出含糊其辞的回答。

✅ 正确做法 与其把所有的信息都塞进去，不如经过精心的设计和组织， 确保模型看到的是准确、有结构、重点突出的内容。

3️⃣ 输入越多，成本越高

大语言模型的调用成本基本上都是按照 Token 来计费的。Token 的数量越多，消耗就会越大。

如果我们不加控制地塞入大量上下文内容，即使效果还行，也可能会带来不必要的开销 —— 尤其是在产品化和大规模使用时。

💡 一句话 优化输入就是优化成本。

所以可以看到，直接把所有资料都发给大模型的方案是行不通的，这里存在很多问题。 那该如何解决它们呢？这就引出 Context Engineering 了。

🛠️ 三、Context Engineering 是什么

不改变模型，只改变模型看到什么

Context Engineering 翻译成中文就是上下文工程。从字面上来看， 它似乎就是针对 Context 所做的一些技术。回想一下 Context 的含义 —— Context 代表给模型的输入，那 Context Engineering 的含义就是对模型输入做优化了。

简单来说，Context Engineering 关注的不是怎么训练模型， 而是怎么精心设计给模型的输入内容，让模型在有限的 Context Window 里面尽可能的理解得更准、答得更好、花得更少。

🎯 核心思想 不改变模型的结构，只改变模型看到什么。

其实 Context 这个概念一直都存在，但是 Context Engineering 这个词确实最近一段时间才活起来的。

🔥 四、为什么现在才火起来

两个原因

🎬 05:55 · 流行的两个原因：模型已足够强大、Agent 的兴起

1️⃣ 模型已足够强大

跟一两年前的模型相比，现在的模型强大的不是一点半点。对于现在的模型来说， 你只要给到它足够精细的要求，给到它足够完整的相关资料， 模型就可以给出非常准确、有用的回答。

⚠️ 一个反直觉的判断 在大部分情况下，如果模型的回答不能让你满意，这并不是因为模型不够强， 而是因为你没有给到模型足够清晰和足够完整的信息。而这一点，正是 Context Engineering 要解决的问题。

2️⃣ Agent 的兴起

Agent 是一种把大模型和工具结合起来，让模型能够独立感知环境、影响环境，从而解决用户问题的技术。

Agent 的运行涉及到模型对工具的使用，所以可用工具信息、工具执行结果等等一系列的内容， 都会放到模型的输入里面。使用多少次工具，就会有多少个工具执行结果。

🚨 Agent 运行时间长了会怎样 Agent 的运行时间长了，这些工具的执行结果就会占满整个 Context Window， 从而影响到模型后续的回答效果。
这也就是为什么 Agent 兴起之后，Context Engineering 的话题也就随之火了起来 —— 因为 Context 的管理效果会直接影响到 Agent 的执行结果。

💾 六、实现方法 ①：保存 Context

把信息存起来，需要时再取

保存 Context 就是说，我们把 Context 做个筛选、总结，并且找个地方保存起来 （比如内存、硬盘这类的地方），在模型需要的时候再发给模型。

🎬 07:10 · 保存 Context：对 Context 做筛选 / 总结，再找个地方存起来

这里一个比较典型的例子，就是 ChatGPT 的记忆功能。

比如我可能在某次聊天的过程中告诉它：我的名字是马克，我有一个频道叫做马克的技术工作坊， 在这个频道里面我分享过关于 Agent、RAG、MCP、A2A 等相关的内容，记住这些！

🎬 07:40 · 注意到「Updated saved memory」了吗 —— 这代表 ChatGPT 把内容存入记忆库

注意到这个 Updated saved memory 了吗？这就代表 ChatGPT 把这段内容存入到它的记忆库里面去了。 我们可以打开记忆库来证实这一点。

✅ 这一步的意义 这个保存的动作，是 Context Engineering 的第一步， 它解决了信息持久化的问题。

但光存下来还不够。ChatGPT 的记忆库是可以存放很多条记录的， 那在未来的对话中，ChatGPT 是如何从这个庞大的记忆库里面精准地找到它所需要的信息呢？ 这就引出了下一个，也就是最核心的技术 —— 选择 Context。

🎯 七、实现方法 ②：选择 Context

最核心的一环：从海量信息里挑出当下需要的

所谓选择 Context，就是从海量的信息中选择出一部分与用户问题最为相关的内容， 并且把它们放在模型的 Context 里面。

💡 为什么说它最核心 一个好的选择策略，是整个系统高效准确运行的保障。

作者把选择策略分为两类：静态选择和动态选择。

🎬 09:50 · 静态选择（Cursor Rules / CLAUDE.md）与动态选择（挑选记忆 / 挑选工具）

📌 静态选择

  • 永远重要、必须遵守的信息
  • 每次请求都全部放进 Context
  • 像刻在 AI 脑子里的系统指令 / 核心原则
  • 例：Cursor Rules、CLAUDE.md

🔄 动态选择

  • 选择与用户问题最相关的内容
  • 不是全塞，而是按需挑选
  • 像一个聪明的图书管理员
  • 例：挑选记忆、挑选工具、RAG

📌 静态选择：全都要

静态选择就是把一些永远重要、必须要遵守的信息，在每一次请求时都全部放到 Context 里面。 它就像是给 AI 刻在脑子里的系统指令，或者是核心原则。

比如 Cursor 的 Rules 文件、Claude Code 的 CLAUDE.md 文件 —— 这些文件指定了当前项目的一些信息、编码时需要遵守的一些规范等等。 这些信息至关重要：无论用户问什么，这些信息都必须在场， 以确保 AI 的行为符合预期。

✅ 策略：对于这类信息，最有效的做法就是「全都要」 只要确保它们加起来不会撑爆 Context Window 就行。

🔄 动态选择：精准挑

动态选择是指选择与用户问题最为相关的内容，并且把它放入到 Context 里面。 它不是把所有的东西都塞进去，而是像一个聪明的图书管理员，为你精准地找到需要的那几页。

比如 ChatGPT 从记忆库中挑选与用户问题最为相关的记忆，这就是一种动态选择。 再比如我们从包含数十个甚至数百个工具中，挑选与用户问题最为相关的三个工具放到模型的 Context 里面， 这也是一种动态选择。

📚 动态选择最有名的实现方式：RAG 检索增强生成（RAG）本质上就是一种动态选择 —— 从知识库里挑出与问题最相关的片段。 本知识库另有 RAG 工作机制详解 与 使用 Python 构建 RAG 系统 两篇可以配合阅读。

🗜️ 八、实现方法 ③：压缩 Context

历史消息越积越多，得想办法瘦身

Agent 运行时会在 Context 里面积累大量的历史消息。一般来说，这些历史消息中最占空间的 便是模型的输出文本和工具的执行结果。

如果不做处理的话，这些历史消息便会迅速占满 Context 的全部空间，从而影响模型的后续回答效果。

一个常见的处理方法就是压缩历史消息。举一个具体的例子 —— 大家熟悉的 Claude Code， 它是一个用于写代码的 Agent。

在它运行的过程中，它可能会读取很多代码内容，同时也会写入很多代码内容， 然后 Claude 可能还会输出一些思考和结论，这些都会放到 Context 里面：

🎬 11:00 · Claude 4 的 Context：读取的 graph.py、写入的 content.txt、Claude 的思考、读取的 category.py、运行终端命令

如果 Claude Code 不对这些内容做处理的话，那么它的 Context Window 很快就会被各种代码信息挤爆。

✅ Claude Code 的处理措施：Auto Compact 当 Claude Code 的使用量超过 95% 的时候，Claude Code 便会运行一种叫做 Auto Compact 的程序，对以往的 Context 做个压缩 —— 其实也就是总结一下之前的内容，然后把原来的内容扔掉。 在总结之后，Context Window 的使用量就会降下来。

用户甚至还可以在 CLAUDE.md 里面指定压缩方案。 比如 Claude Code 官方文档里举的例子，就是让 Claude Code 压缩时重点保留测试输出和代码改动方面的内容：

🎬 11:20 · 官方文档示例：通过 CLAUDE.md 自定义压缩时保留的重点
# Summary instructions
When you are using compact, please focus on test output and code changes

这就把「压缩」从一种固定的自动行为，变成了可配置的策略 —— 你可以告诉它压缩时别丢掉你最在意的信息。

🔒 九、实现方法 ④：隔离 Context

让不同模块各管各的，互不干扰

隔离 Context 意思就是说，不同模块之间的 Context 是互相隔离的、互不干扰。 这通常发生在 Multi-Agent（多智能体）系统里面。

可以用 Anthropic 的一篇文章来举例，它讲述了 Anthropic 是怎么构建他们的 Multi-Agent 研究系统的。 在文章中 Anthropic 提到，系统内部有一个 Lead Agent， 它负责任务下发和归纳总结 —— 你可以把它想象为整个系统的总指挥官。

🎬 12:25 · Lead Agent 下发任务给多个 Subagent：搜索 PDF、搜索网络、搜索图片

整个流程是这样的：

  1. 用户的请求会先打到这个 Lead Agent 里面
  2. 在接收到用户请求之后，Lead Agent 便会把用户的问题下发到其他的 Agent 系统里面 —— Anthropic 称这些 Agent 为 SubAgent
  3. 比如 Lead Agent 可能会先发起一个负责搜索 PDF 的 SubAgent，拿到 PDF 的搜索结果； 再去执行一个负责搜索网络的 SubAgent，拿到网络的搜索结果； 然后再去执行一个负责搜索图片的 SubAgent
  4. 在拿到所有 SubAgent 结果后，Lead Agent 就会产出一份最终的报告给用户看，整个流程也就随之结束
💡 关键点在哪 这些 SubAgent 系统有着自己独立的工具、独立的运行历史、独立的记忆体系 —— 也就是说，这几个 SubAgent 的 Context 是互相隔离、互不影响的。 这就是隔离 Context 的一个非常典型的例子：不同的系统拥有不同的 Context，职责清晰，彼此之间互不干扰。

除此之外，Claude Code 里面也有一个 SubAgent 的概念，跟上面 Multi-Agent 研究系统里面的 SubAgent 有点像， 但并不完全一样。在 Claude Code 中，每个 SubAgent 也都有着自己独立的 Context，互相隔离。

🔗 与 Harness Engineering 的关系 隔离与分工也是 Harness Engineering 的核心手段之一。 本知识库另有 Harness Engineering 到底是什么？ 一篇， 其中 Anthropic 的 planner / generator / evaluator 三 Agent 架构，正是隔离 Context 的另一种落地形式。

⚠️ 这篇文章真正的观点 如果一定要做 Multi-Agent 系统的话，各个 Agent 的运行也必须要串联执行， 并且要做好 Context Engineering，确保给模型的输入简洁明了。
所以在看完这篇文章之后，你可以同时学到 Agent 的构建策略与 Context Engineering 两方面的内容。

问题结论
Context 是什么？模型的输入，包括用户问题、背景信息、相关资料、可用工具列表、工具执行结果、历史对话
Context Window 是什么？模型的输入中最多能包含的 Token 数量
Token 怎么换算？1 Token ≈ 0.75 个单词 ≈ 1.5 个汉字
超过 Context Window 会怎样？前面的内容被丢弃，只保留最后的 N 个 Token
主流模型的窗口有多大？Gemini 2.5 Pro 100 万、GPT-5 40 万、Claude 4 20 万、Deepseek V3 12.8 万
为什么不把所有资料都丢进去？三大问题：窗口有限、输入杂乱会干扰理解、输入越多成本越高
Context Engineering 是什么？精心设计给模型的输入内容，让模型在有限窗口里更准、更好、更省
它的核心思想？不改变模型的结构，只改变模型看到什么
为什么现在才火？① 模型已足够强大 ② Agent 兴起，工具执行结果会占满窗口
有哪四类实现方法？保存 Context、选择 Context、压缩 Context、隔离 Context
什么是保存 Context？把 Context 筛选、总结后存到内存/硬盘，需要时再发给模型；例：ChatGPT 记忆功能
静态选择 vs 动态选择？静态＝永远重要的信息每次全放（Cursor Rules / CLAUDE.md）；动态＝按问题挑最相关的
动态选择最有名的实现？RAG（检索增强生成）
压缩 Context 的典型例子？Claude Code 用量超过 95% 时触发 Auto Compact，总结旧内容并丢弃原文
压缩方案能自定义吗？能，写在 CLAUDE.md 里，例如「压缩时重点保留测试输出和代码改动」
什么是隔离 Context？不同模块的 Context 互相隔离、互不干扰；典型场景是 Multi-Agent 系统
Anthropic 的 Multi-Agent 怎么分工？Lead Agent 做任务下发和归纳总结，SubAgent 分别搜 PDF / 网络 / 图片，各自有独立 Context
Context Engineering 是某一项技术吗？不是，它是某一类技术的统称
